## 3. Decisions waiting on the product owner

These are the next things to settle. The first four reshape many facts, so make them before owners sign items, or the items will need signing again.

1. **Refine decision 4 into three classes of fact.** Decision 4 (docs/plan-colorado.md) says missing information means "cannot determine" unless the rule says otherwise. It has been applied as "required wherever read", and that is most of the burden the service-design review found. The proposal:
   - **Required.** Missing means cannot determine: date of birth, income, immigration status.
   - **Rule default.** Missing takes the rule's own default, with its citation: an unclaimed deduction is 0 (7 CFR 273.2(f)(3)(ii)), a disqualification exists only if an authority found one, an exception applies only if claimed.
   - **Screened.** A household yes/no question, with person-level detail required only on yes.

   No stored answer changes. Rule tests that pin cannot-determine would be rewritten. Source: docs/reviews/service-design-fact-burden.md.
2. **Adopt the four tests for what may be shared across programs as a governance rule.**
   - The tests:
     - T1, observable without any program's rule;
     - T2, not redefined by any reading program's paragraph;
     - T3, one value right for every period read, or the change dated;
     - T4, derived items only, mechanical (date logic, arithmetic, relationships).
   - What passes: T1–T3 make a primitive; a derived item that also passes T4 is a clean derivation.
   - Grey items: an item that passes T1 but fails T2 or T3 is grey, and is split into a neutral primitive plus each program's own reading.
   - Enforcement: a check in `npm run check` that refuses a shared item whose description cites one program's paragraph, or whose derivation reads a program-prefixed item.

   Source: docs/reviews/cross-program-primitives.md (rubric, classification of all 272 shared items) and .json (per-item reach and class).
3. **Pregnancy model.** Ask "Is anyone pregnant? Who?" once for the household, then the number expected and due date for each person named. Keep the stored fact per person (`is_pregnant` plus dates), defaulting to false for those not named. This handles two pregnant people and keeps Medicaid and CHP+'s per-person reads. Do not filter who can be named by sex or age. 42 CFR 435.956(e) allows self-attestation. Also merge the three program copies of "pregnant in the month", which already disagree (XP-8).
4. **Benefit status stated once.** A receipt record for the month is the evidence of receiving SSI, TANF or Adult Financial. A narrow status record covers status without payment (1619(b), approved but unpaid, suspended), each with its reason. The 62 stored disagreements (28 SSI, 18 TANF, 16 AF) are each sorted as one of:
   - a test-data error, which is fixed;
   - status without payment, which moves to the status record;
   - a payment that isn't the person's own status (retro lump sum, payee for someone else), which is marked on the receipt.

   Add a check that fails a status flag with no receipt and no stated reason. List every answer that moves before merging.
5. **Screening guardrails** for any front end (docs/reviews/screening-order.md): it may reorder and skip questions and say "likely not eligible; you may still apply". It may not:
   - block filing, or record a denial;
   - let one program or category stand for another;
   - close a program before every pathway is closed;
   - read silence as an answer;
   - carry one month's result into another.

  - assumptions and exclusions.
- **Planner:** https://claude.ai/artifact/SS5mFSXabtxpTMakKoNs6L (source docs/planning/review-planner.html). A what-if calculator for time per tier and each role's hours, reviewers and sign-off-and-meeting hours.
- **Effort tiers:** a rule of thumb, not a judgement on each item.
  - Easy: a primitive fact, a short rule (15 terms or fewer), or a single dated figure.
  - Hard: an outcome, household or unit composition, a long rule (more than 80 terms), or a grey shared fact.
  - Questions by breadth: one program and up to 2 items is easy; several programs or 6 or more items is hard.
  - Examples:
    - Easy: date of birth; a person's SNAP gross income; SNAP elderly age.
    - Medium: SNAP medical expenses at last certification; Adult Financial countable vehicles; the SNAP gross income limit by household size.
    - Hard: state of residence; lives with; SNAP allotment (an outcome); the five-year rule exemptions for refugees and asylees.

## 9. How to work in this repo (lessons that cost time)

- **Branch and commits.** Push only to `ccr-9d19bf4c-wmnwcl`. End commit messages with the two trailer lines the session's attribution note gives: `Co-Authored-By` and `Claude-Session`. Never put model names in files or commits. PR comments end with the "Generated by Claude Code" footer. Do not run worktree cleanup without asking the product owner.
- **Gate before every push.** In order:
  1. `node scripts/sync-manifest.mjs co`
  2. `npm run typecheck`
  3. `npx vitest run`
  4. the record checks: `npm run receipts:harness`, `npm run records:harness -- --list earnings` and `-- --list holdings`
  5. `CHECK_BASE=origin/main npm run check`, which takes about 10 minutes, so run it in the background.

  Commit before `check`: it counts dispositions only on committed changes.
- **Harness rules.** Since E2 and H2 the record checks are the metamorphic relations and the two lints; there is no old-against-new comparison and no allowed-differences file, so a change that moves an answer shows in the rule tests and household expectations (`npm run check`) and is disclosed in its change record. Acceptance logic is never edited. A new receipt money field must be added to the metamorphic split list, with a comment. A household or rule test states income and resources in the records alone.
- **Change impact.** A change to an item flags the items that read it. Disposition each flag in a dated change record (volumes/co/changes/*.yaml), as either "applies" with the reason or "not_applicable" with the reason. Two formats exist: YAML and JSON-quoted. A fingerprint moved only by upstream changes is re-keyed with every earlier reason kept.
- **Parallel rounds.**
  - Give each agent disjoint item, household, source and OQ ranges, and name the items the others are editing.
  - Conflicts recur in five places:
    - volumes/co/tests/cases.yaml: append-only; rebuild from clean appends and check it parses;
    - volumes/co/open-questions.md;
    - known-limits.md: keep one section per program;
    - the UI pin counts in test/ui/*.test.ts*: re-pin with a comment giving each side's value;
    - codex.json: regenerate.
  - Git can merge a pin line silently to a wrong value, so run the tests after every merge.
  - Use at most four agents at once.
- **Reviews.**
  - Every fix round's own tests have missed something, so an independent reviewer checks each round. Give it the code and the cited paragraphs, not the fixer's conclusion.
  - Reviewers write probes as households; the probes become stored households.
  - Never write rule text from memory: quote the fetched text in volumes/co/documents/.
  - Open questions must be classed: a state policy choice, or blocked on a named document.
- **Tools.**
  - `npx vite-node scripts/eval-case.ts co <case> <identifiers>` shows values and missing facts.
  - Probe runners from the reviews (scratch, not committed) load a YAML household through src/engine.
  - The pattern sweeps are scripts/audit/pattern-sweep*.ts; `--anchors` finds date anchors and time-varying parameters read once.
